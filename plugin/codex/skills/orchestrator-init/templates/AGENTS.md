# Orchestration rules

This folder coordinates work across project repos: it plans, dispatches T3 threads, records results and reports. It never edits project code itself. Fill every `<placeholder>` before the first progress check; delete a section you do not use.

## Layout

`{{orchestrator_dir}}`: `bin/ state/ plans/ learnings/ flakes/ skills/ schedules/ inbox/ outbox/`. The scripts in `bin/` resolve paths from their own location, so the folder can move. Evidence (screenshots, logs, traces) lives in `~/orchestrator-artifacts/<task>/<run-id>/`, never in this folder or a project repo.

## People and approvals

- {{approver}} scopes tasks, approves plans, approves every thread spin-up and spin-down, approves every push, and is the only one who closes {{tracker}} cards.
- Nothing is written to {{tracker}}, chat tools or calendars without {{approver}}'s explicit yes on a numbered draft.
- Other people: <name> (<role>), <name> (<role>).

## Records

- One state file per task, `state/<TASK-ID>.yaml` (format in `state/SCHEMA.md`). Change it only with `bin/state.py`. `PROGRESS.md` and `PROGRESS-digest.md` are generated by `bin/render-progress.py`; never edit them.
- One plan per task, `plans/<TASK-ID>/plan.md` from `plans/TEMPLATE.md`. {{approver}} approves the plan before execution; approving a plan approves every task in it.
- Read `learnings/<project>.md` and `flakes/<project>.md` before planning. One flake entry per known intermittent failure: signature, discriminator, rerun cap, disposition.

## The cycle

1. **Intake**: {{approver}} selects a card; record it in a new state file.
2. **Research**: open questions come back in the report; relay them to {{approver}}.
3. **Plan**: epics, tasks, security invariants, parallelism, review assignments. {{approver}} approves.
4. **Design**: for UI tasks, before they execute.
5. **Execute**: one thread per task, in the T3 project of the repo it works on, on a worktree cut from the target branch.
6. **Review**: one remote code review per delivered task, one fix round.
7. **Learnings**: lessons go to `learnings/`, flake entries to `flakes/`.
8. **Close**: when every epic is done, report; {{approver}} tests and closes the card.

## Threads

- Every task, review or fix round runs in its own new T3 thread named `<TASK-ID> / <what>`, with the model set explicitly from the routing table. This thread only coordinates: it reads results and writes state, inbox and outbox.
- A thread that needs a push ends its turn with "commit done, push pending approval"; this thread never approves a push and lists every pending push in its next reply.
- Task threads read the project repo's own rules (`AGENTS.md`, `CLAUDE.md`), not this file.

## Model routing by complexity

Before every launch, post a numbered draft: the task, its tier, the field (frontend, backend, infra, security, review, research, planning) and the candidates for that tier. Launch only after {{approver}} answers with a number. Record provider, model and effort on the run.

| Complexity | Candidates (provider / model / effort) |
| --- | --- |
| Trivial: a one-line, copy or config change with no test to write | |
| Simple: one file or one well-defined change, no design decision | |
| Medium: several files or one module, needs tests and a review | |
| Complex: cross-module, architecture, migrations, security-sensitive or unclear scope | |

## Inbox and outbox

`inbox/` is to this thread, `outbox/` is from it; the format is in each folder's `README.md`. Files without `approved_by: {{approver}}` are read but never acted on. Handled files move to `done/`.

## Progress check

- T3 scheduled task `Orchestrator progress check`, every 45 minutes, bound to this thread in T3 project `<T3 orchestrator project id>`. Its prompt is `schedules/progress-check.md`. Schedule id: `<schedule id>`.
- On only while approved work is running or queued. After three checks with no change on every task, or when no approved step can proceed, it records the blocker, asks {{approver}} and disables itself. An inbox file, a delegated-task notification or {{approver}}'s message turns it back on.
- Write `next_step` as a quoted plain string. A done task's `next_step` is "none".

## Config review (bi-weekly)

T3 scheduled task `Config review (bi-weekly)`, every 14 days, bound to this thread. Its prompt is `schedules/config-review.md`. Schedule id: `<schedule id>`. It writes `plans/config-reviews/<date>.md` with a numbered proposal and applies nothing; {{approver}} picks the numbers.
